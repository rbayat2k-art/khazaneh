# ADR-018 — تنظیمات مشترک اتصال استعلام در همه محیط‌ها

## وضعیت و اختیار

مصوب مالک، ۲۰۲۶/۱۰/۲۴: تکمیل تنظیمات اتصال و انتشار پس از آزمون روی دامنه. این تصمیم محدودیت Staging-only مدیریت اتصال در ADR-012/013 را برای همین تحویل جایگزین می‌کند؛ انتقال کلید یا دادهٔ Staging به Production، فراخوانی واقعی آزمایشی با اطلاعات مالک، فعال‌سازی پیامک و API ناشناخته را مجاز نمی‌کند.

## تصمیم و مرزها

- نام اتصال، نگهداری رمزنگاری‌شده و write-only کلید، انتخاب صریح، metadata و تست اتصال مشترک‌اند. فرم در مدیریت اطلاعات پایه می‌ماند؛ خزانه فقط وضعیت و ابزار عملیاتی را می‌بیند. خاموش‌بودن شبکه باعث ناپدیدشدن فرم نمی‌شود؛ نبود storage پیام صریح دارد.
- قرارداد هر ارائه‌دهنده مستقل است: registry آزموده‌شده، نوع و فیلدهای credential، پارامتر/پاسخ و مجوز شبکه. فعلاً فقط قرارداد REST قبلی پیاده شده است. endpoint و روش احراز هویت آن readonly نمایش داده می‌شوند؛ کاربر URL/header/parser اجرایی دلخواه نمی‌سازد. سرویس دیگر نیازمند مستندات بدون secret و adapter/allowlist آزموده‌شده است، نه صرفاً کلید متفاوت.
- Production از `TREASURY_INQUIRY_VAULT_DIR` خصوصی و ازپیش‌تأمین‌شده استفاده می‌کند؛ catalog1/KEK موجود و CAS/blank-preserve بدون تغییر فرمت حفظ می‌شوند. `TREASURY_INQUIRY_NETWORK_ALLOWED=true` فقط اجازهٔ شبکهٔ استعلام است؛ guard سراسری پیامک/بانک‌های دیگر تغییر نمی‌کند. تمام LIVEها، حتی env legacy، این flag را لازم دارند. Stage ناقص از مسیر Production استفاده نمی‌کند؛ broker و manual-only آن محفوظ‌اند.
- ذخیره/انتخاب کلید هیچ dispatch یا تغییر DB ایجاد نمی‌کند. LIVE برای شروع مصرف، نسخهٔ اتصال و تأیید صریح مدیر دربارهٔ ارسال کارت، شرکت‌ها، سقف و خودکار/دستی را لازم دارد. کلید آمادهٔ ذخیره با مجوز مصرف یکی نیست. تست اتصال/اعتبار، اقدام جداگانه و بدون شماره کارت است؛ موفقیت فقط پس از پاسخ معتبر ارائه‌دهنده نمایش داده می‌شود.
- binding از source/provider/profile/generation ساخته می‌شود؛ بعد از تغییر کلید یا اتصال، مجوز مصرف قبلی معتبر نیست. callback مجوز در auto-candidate و claim/pre-dispatch/apply اجرا می‌شود؛ خطا/نبود binding fail-closed است. پاسخ دیرهنگام نمی‌تواند رکورد مالی را تغییر دهد.
- رد قطعی پیش از ساخت operation جدید، وضعیت400 دارد تا handle تازهٔ مرورگر قفل نشود. retry/replay/conflict موجود و شکست commit مبهم، همان حفاظت قبلی را حفظ می‌کنند.

## داده و بازیابی — KHZ-INQUIRY-CONFIG-v51-001

schema SQLite1 و فرمت vault1 تغییر نمی‌کنند. `connectionVersion` اختیاری در config، فقط هنگام ذخیرهٔ صریح تنظیمات LIVE نوشته می‌شود؛ config قدیمی بدون آن خودکار مجوز مصرف نمی‌گیرد. نیاز به backfill یا بازنویسی سوابق/مبالغ نیست. خاموش‌کردن صریح سرویس binding را حذف می‌کند. تمام رفتارهای مالی، شرکت/مجوز، سقف، operationKey، عدم بازنویسی شبای موجود و تأیید نام با دلیل محفوظ‌اند.

vault خارج data/release/document-root است؛ snapshot سازگار انتشار باید catalog و KEK را با هم و همراه DB/config/files حفاظت کند. rollback، کد با DB و vault **جاری** است؛ بکاپ قدیمی روی نوشتن‌های جدید restore نشود. بازیابی جفت DB/vault با شبکه خاموش انجام شود و تا پذیرش مجدد اتصال باز نشود؛ AES-GCM مانع replay بکاپ قدیمی نیست. KEK مفقود/خراب جایگزین خودکار ندارد. در Windows ACL و Linux owner/mode و مسیر واقعی کنترل شوند.

## پذیرش

RED نسخه Production، unit پرچم‌ها/legacy، API واقعی/SQLite، CAS و failure/restart، تعویض کلید حین ارسال، لغو نشست حین credit و مرورگر desktop/mobile لازم‌اند. فقط provider در آزمون مصنوعی است؛ auth/API/storage واقعی‌اند. تکرار فشار مالی v50 لازم نیست مگر مسیر صف/ثبت عمومی تغییر کند؛ این مرحله ظرفیت تازه را تضمین نمی‌کند. نتیجه و manifest واقعی از سند عملیات v51 خوانده شوند؛ این ADR اثبات اجرا یا ارسال واقعی نیست.
