# ADR-025 — تکرار محدود جابه‌جایی اتمیک JSON در ویندوز

Accepted — درخواست صریح مالک۲۰۲۶/۱۰/۲۵ برای رفع مانع v59b، آزمون و تحویل فقط Staging؛ Production و commit/push مجاز نیستند.

## هدف و مرز

در آزمون مصنوعی Windows، fs.renameSync با EPERM مواجه شد. دو suite کامل JSON در انتظار نتیجه استعلام و آزمون وابسته شکست خوردند؛ trace اجرای اصلی موجود نبود و همان علت برای آن اجراها قطعی ادعا نمی‌شود. اصلاح باید خطای sharing گذرا را تحمل کند، بدون حذف مقصد، بازنویسی غیراتمیک، تغییر اختیار/رمز/مبالغ یا اجرای دوباره فرمان/بانک/پیامک. [ADR-024](ADR-024-shared-organization-source-bank-accounts.md) و تغییر حساب‌های مشترک حفظ می‌شوند.

## قرارداد

saveDb همگام و نوبت نویسنده موجود حفظ شود. serialize/write/fsync/fstat همان یک candidate فقط یک‌بار انجام می‌شوند. helper فقط rename همان فایل موقت به مقصد را روی Windows و فقط برای EPERM/EACCES/EBUSY حداکثر شش تلاش با انتظار۱۰،۲۰،۴۰،۸۰،۱۰۰میلی‌ثانیه (جمع۲۵۰ms، به‌جز هزینه خود IO) تکرار می‌کند. این کدها به‌تنهایی موقتی‌بودن خطا را اثبات نمی‌کنند؛ پس سقف ثابت و fail-closed لازم است. خطای دیگر یا غیرWindows فوری شکست است. برای حفظ امضای saveDb، انتظار کوتاه همگام است؛ loop نامحدود، async تغییرنکرده caller و تنظیم env برای دورزدن سقف نداریم.

assertCurrent پیش از هر تلاش و پس از انتظار خارج catch قابل-retry اجرا می‌شود. draft تازه/normalize مجدد/CAS جدید ساخته نمی‌شود. publish فقط یک‌بار پس از موفقیت rename و با metadata اصلی فایل موقت است؛ خطای publish retry نمی‌شود. EIO/ENOSPC/EXDEV/ENOENT و تغییر خارجی نباید باعث تکرار دامنه یا بازگردانی مقصد شوند. شکست پیش از rename همان DB و snapshot قبلی را نگه می‌دارد؛ فایل موقت خصوصی همان رفتار retaining قبلی را دارد و هیچ فایل مقصد/نامرتبط حذف نمی‌شود. SQLite/schema۱ و مسیر تراکنش آن تغییر نمی‌کنند.

## پذیرش و ترتیب کار

۱) RED قطعی برای rename sharing و assertCurrent روی retry؛ سپس helper کوچک و اتصال همان saveDb. ۲) تست Windows/غیرWindows، دائمی/غیرمجاز، bytes یکسان، سقف انتظار، عدم publish زودهنگام، تغییر خارجی/metadata، restart و نوبت نویسنده. ۳) تزریق sharing روی commit پرداخت و ثبت نتیجه استعلام؛ هرکدام یک اثر/رسید/lookup منطقی و شکست دائمی بدون موفقیت کاذب؛ EIO فعلی همچنان fail شود. ۴) artifact واقعی، suite کامل هر دو adapter و چند تکرار متمرکز استعلام JSON بدون افزایش timeout/skip، مرورگر و recovery. ۵) مرور مستقل و بکاپ جاری Stage/restore مستقل با حفظ state، ACCESS و vault، سپس همان artifact فقط روی Staging. خطای gate مانع انتقال است.

داده قدیمی backfill/reset نمی‌شود. برای بازگشت، CURRENT state/vault و binary سازگار با metadata manual و مسیرهای v58 لازم است؛ restore بکاپ قدیمی روی نوشتن تازه مجاز نیست. ناپایداری‌های نامرتبط و پنج finding قدیمی v55، رفع‌شده معرفی نمی‌شوند. نتایج و محدودیت‌ها در رکورد عملیاتی تازه ثبت می‌شوند.

تحویل اجراشده: [v60 فقط Staging](../operations/staging-v60-windows-json.md)، همان artifact با هر۴۷۸تست هر adapter و پنج تکرار استعلام موفق؛ محدودیت‌های قفل دائمی و عدم انتشار Production در رکورد صریح‌اند.
