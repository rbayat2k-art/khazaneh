# ADR-022 — تأییدکننده مستقل هر نوع درخواست برای هر کاربر

Accepted — تصمیم نهایی مالک۲۰۲۶/۱۰/۲۴، فقط پیاده‌سازی و Staging. مجوز Production یا commit/push نیست.

الحاقیهٔ بعدی همان روز: [ADR-023](ADR-023-explicit-direct-accounting-per-request-type.md) با درخواست تازه مالک، فقط محدودیت «بدون گزینه مستقل مستقیم به حسابداری» را جایگزین می‌کند؛ قرارداد سه‌حالته و حفاظت‌های تازه آن مرجع‌اند. متن زیر سابقه تصمیم v58a است.

## تصمیم و مرز

چهار نوع ADVANCE_SINGLE / ADVANCE_BATCH / PAYMENT_SINGLE / PAYMENT_BATCH برای هر کاربر override اختیاریِ شناسه تأییدکننده دارند. نبود override یعنی همان User.supervisorId سازمانی؛ نبود هر دو، طبق تصمیم قبلی مستقیم حسابداری و **بدون ساختن تأیید سرپرست** است. داشتن چند نقش مسیر را عوض نمی‌کند. خودتأییدی، گردش چندمرحله‌ای، تغییر scope/سقف/شرکت و انتقال درخواست قدیمی در این تحویل نیستند. پیشنهادهای قبلی خودتأییدی با انتخاب نهایی مالک وارد این نسخه نمی‌شوند؛ استثنای قبلی ADMIN بازطراحی نمی‌شود و override خودی برای همه ممنوع است.

assignee درخواست، همان parent.supervisorId/name موجود است و فقط هنگام ثبت جدید resolve می‌شود. اصلاح، ارسال مجدد، اعلان، عودت فنی و گزارش از snapshot همان درخواست استفاده می‌کنند؛ تنظیم جدید به معنی انتقال پرونده قبلی نیست. گروه، maker واقعی واحد دارد؛ نام گیرنده، هویت ثبت‌کننده نیست. دستور خارج سامانه و پرداخت دستی مسیر قبلی را حفظ می‌کنند.

## قرارداد و حفاظت

User.requestApprovers اختیاری و sparse است؛ مقدار هر کلید، شناسه موجود غیرخودی با مجوز/شرکت/scope/سقف مثبت معتبر است. خالیِ انتخابگر، کلید را حذف می‌کند؛ گزینهٔ مستقلِ دورزدن تأیید اضافه نمی‌شود. مرجع نامعتبر، بی‌صدا fallback نمی‌شود. سقف ریالیِ اقدام همچنان در review و طبق قرارداد جاری سنجیده می‌شود؛ قانون مالی جدیدی برای جمع گروه/آستانه ثبت ایجاد نمی‌شود.

users/save در صورت ارسال requestApprovers برای کاربر موجود، expectedRequestApprovers هم می‌خواهد؛ مقایسه در همان صف نویسنده است و ناسازگاری409 بدون تغییر می‌دهد. کلاینت قدیمی که این فیلد را نفرستد، تنظیم فعلی را حفظ می‌کند. تغییر مسیر حساب خود توسط actor ممنوع است؛ سایر حدود مدیریت کاربر جاری حفظ‌اند. تغییرات مسیر audit جدا با قبل/بعدِ شناسه‌ها دارد؛ رمز یا اطلاعات بانکی وارد سابقه نمی‌شود.

وابستگی overrideهای آینده نیز هنگام کاهش صلاحیت/غیرفعال‌سازی/حذف تأییدکننده محافظت می‌شود؛ تنظیم‌ها ابتدا صریحاً تعیین تکلیف شوند. کارهای موجود با snapshot قبلی بررسی می‌شوند و جانشینی سازمانی، override مستقل را جابه‌جا نمی‌کند. هیچ نقش یا داده‌ای خودکار اعطا/بازنویسی نمی‌شود. schema SQLite۱ ثابت؛ فیلد افزایشی، بدون migration/backfill/reset.

## اجرا و گیت

مسیر کار: مدل/parse مشترک → اعتبارسنجی users/save و وابستگی → resolver سه فرمان ثبت → فرم چهارانتخابی → تست مثبت/منفی/CAS/رقابت/rollback/reload/اعلان → build منجمد و هر دو adapter → مرورگر → بکاپ و restore مستقل Stage جاری → Staging و پذیرش مالک. primary sole writer؛ بازبین خواندنی متصل به command/authorization است. نامزد باید v56c و اصلاح منتشرشده بانک v57b را حفظ کند؛ checkout فعال با Production برابر نیست.

پذیرش: هر چهار مقصد مستقل، fallback قدیمی و مدیر بدون سرپرست صحیح؛ تأیید/مشاهده فقط برای assignee واجدصلاحیت، خودی و خارج شرکت/scope ممنوع؛ متقاضی قادر به جعل مسیر در submit نیست؛ تنظیم و داده/رمز/نقش قبلی محفوظ؛ تغییر تنظیم، اسناد قبلی و اصلاح آن‌ها را جابه‌جا نکند؛ شکست commit و CAS/race اثر ناقص نسازند؛ مرورگر RTL/mobile و reload واقعی؛ تماس واقعی و Production NOT RUN.
