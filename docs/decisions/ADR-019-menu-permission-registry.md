# ADR-019 — منوها و عملیات قابل تنظیم با حفظ اختیار موجود

## وضعیت و دامنه

الحاقیهٔ پذیرش: مالک پس از تست Staging، انتشار دقیق v53f را با حفظ اطلاعات، رمزها و دسترسی‌های فعلی صریحاً تأیید کرد. [رکورد انتشار Production](../operations/release-v53-menu-permissions.md) نتیجه و روش بازگشت را ثبت می‌کند. قید Stage-only در شرح اولیهٔ پایین تاریخی است، نه مجوز دائمی نشر؛ هیچ قاعدهٔ تازه‌ای برای افزایش/کاهش مالی نقش‌ها اتخاذ نشد.

مصوب برای توسعه و آزمون Staging،۲۰۲۶/۱۰/۲۴؛ انتشار Production مجاز نیست. درخواست مالک: رفع یافته‌های [ممیزی v52](../engineering/access-menu-audit-v52.md)، کارت مستقل با نام دقیق هرمنوی اصلی و همه زیرمنوهایش،ظاهر استاندارد،بدون تغییر خودکار دسترسی کاربران.

## تصمیم

Registry مشترک، عنوان/گروه/نوع/پیش‌نیاز گزینه‌ها و ناوبری را تعریف می‌کند؛ فرم،shortcut،counter و انتخاب landing ازآن استفاده می‌کنند. گزینه‌های واقعی موجود مخفی نمی‌مانند. اختیار ثبت `canSubmit*` از نمایش فرم `canCreate*` صریحاً جداست؛ تعارض قدیمی بدون اطلاع مدیر synchronize نمی‌شود. مجوز کلی ثبت و ارسال مجدد، مدیریت حساب،ثبت دستی،بستن روکش و مشاهده آرشیو کنترل واضح دارند. دو کلید قدیمی مشاهده/اعلان خزانه هنوز مصرف امنیتی دارند؛ مقدارشان محفوظ و درتنظیمات توضیح‌دار است،نه aliasبی‌اثر.

هر زیرمنوی فاقد کنترل مستقل، یک flagاختیاری `canShow...` برای **نمایش و ناوبری** می‌گیرد؛ درنبود مقدار، دقیقاً ازرفتار قبلی ارث می‌برد. این flagها جایگزین مجوز خواندن داده،شرکت،مرحله،ثبت،تأیید،سقف یاپرداخت درسرور نیستند و عنوانشان «نمایش» است. API مالی باخاموش‌شدن صرفِ نمایش،مجاز/غیرمجاز نمی‌شود؛ اختیار عملیاتی خودش باید تنظیم شود. flags درstartup خودکار materialize یاgrantنمی‌شوند. صفحهٔ تغییررمز/نشست خودکاربر به‌علت پنهان‌کردن منوی تنظیمات قفل نمی‌شود.

ذخیرهٔ عنوان یا گزینهٔ نامرتبط، مقادیر عملیاتی قبل را تغییر نمی‌دهد. سرور patch بولین مجاز را بر **snapshot normalized قبلی** اعمال می‌کند؛ مقدار غیربولین یا اختیار ناشناختهٔ جدید رد می‌شود. برای سازگاری کلاینت قدیمی، بولین ناشناخته فقط وقتی عین مقدار ذخیره‌شده باشد پذیرفته و بدون تغییر حفظ می‌شود. ذخیرهٔ نقش‌های فعلی migration/reset نمی‌خواهد؛ schema SQLite همان۱ می‌ماند. اختیار جدید مالی یا تفکیک قانون رد/برگشت/پرداخت اختراع نمی‌شود؛ گزینه‌های مشترک در UI صریحاً مشترک معرفی می‌شوند.

در چندنقشی، اگر flag نمایش در همهٔ نقش‌ها غایب باشد، fallback از حقوق مؤثر نهایی محاسبه می‌شود تا پیش‌نیازهای مرکبِ قدیمی حفظ شوند. پس از تنظیم صریح، true نقش‌ها با نمایش ارثی خودِ نقش‌های فاقد مقدار جمع می‌شود؛ نقش نامرتبط نمی‌تواند گزینهٔ خاموش نقش دیگر را دوباره روشن کند. override شخصیِ صریح مقدم است. این اجتماع فقط ناوبری است، نه تغییر قواعد مالی یا شرکت‌ها.

برای مدیر محدود به شرکت، DTO سرپرست فقط اشتراک شرکت‌های مجاز مدیر و سرپرست را برای انتخاب معتبر می‌دهد؛ catalog نقش‌های گسترده‌تر افشا نمی‌شود. این فیلد فقط projection است و در رکورد کاربر ذخیره نمی‌شود. poll یکسان سرور draft ذخیره‌نشده را بازنشانی نمی‌کند؛ bulkهای ADMIN غیرفعال‌اند تا اختیارات اجباری فعلی تغییر نکنند.

سرپرست انتخابی باهمان معیار شرکت‌های مجاز چندنقشی،scope،مجوز و سقف سرور فیلتر می‌شود؛ رابطهٔ موجود خودکار پاک نمی‌شود. خطاهای شرکت/واحد/مجوز/سقف جدا هستند. landing فقطtabمجاز را بازمی‌کند؛ پنهان‌شدن منو بهنمایش فرم نامرتبط منجر نمی‌شود.

## مسیر و برنامهٔ اجرا

۱.registry و تست قرارداد/حفظ مقادیر؛۲.فرم نقش و shortcut/counter؛۳.Sidebar/App/landing؛۴.سرور patch و علت سرپرست؛۵.regression هرJSON/SQLite و مرورگر همه نقش‌ها؛۶.freeze/backup/restore و Staging مستقل باهمان رمزهای Stage؛۷.تحویل لینک و مسیر امن رمز بهمالک. کد/اسناد قبلی وProductionبدون تغییر باقی بمانند.

## پذیرش و آزمون

- تمام منوها/زیرمنوهای فعال درregistry و فرم تنظیم قابل ردیابی،با نام دقیق sidebar.
- انتخاب‌همه شامل استعلام وارسال مجدد؛شمارش واحد،RTL/mobileبدونoverflow.
- نمایش و عملیات مستقل،نام‌گذاری بدون ادعایgrant؛تغییر عمل واقعاًدرسرور و همان نشست اثرکند.
- تنظیم‌نکردن گزینهٔ تازه،ذخیرهٔ نام یاویرایش نامرتبط،اختیار قدیم/تعارض صریح را تغییرندهد؛مقادیر اولیهٔ مصنوعی قدیمی وتمام حالت‌هایtrue/false/undefined آزمایش شوند.
- scope/شرکت/سقف/نسخه/چندنقشی،deny،نشست،race/retry،مالی وپیوست‌ها regressionسالم بمانند.
- Stagingمصنوعی باDB/vault/نشست مستقل،خدمات خارجی بسته،رمزها محفوظ؛ هیچ تغییر/نشر Production دراین تحویل.
