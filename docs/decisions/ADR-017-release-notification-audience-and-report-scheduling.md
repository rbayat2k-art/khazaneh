# ADR-017 — مخاطب اعلان و زمان‌بندی گزارش برای انتشار v50

تاریخ: ۲۰۲۶/۱۰/۲۳. وضعیت تصمیم: پذیرفته؛ انتشار فقط طبق گزارش نسخه واقعاً نصب‌شده.

## علت

آزمون نهایی مالک، ارسال پیامک به اولین مشاهده‌گر مدیر به‌جای سرپرست مشخص، حذف مخاطب مرحله بعد با مخلوط‌کردن شخص/نقش، اعلان گروهی بدون هدف واقعی و حذف اعلان‌های تازه در گروه بزرگ را بازتولید کرد. آزمون مستقل Linux با۶۰ نشست واقعی و۱۰هزار سابقه، گزارش‌گیری همگام را عامل افزایش صف ثبت نشان داد.

## تصمیم و قرارداد

- مشاهدهٔ مدیریتی، مخاطب پیامک/اعلان شخصی یا ویندوز نیست. شخص صریح انحصاری است؛ نقش تکمیلی معتبر نیز برای صف لحاظ می‌شود. مجوز جاری رکورد، شرکت، فعال‌بودن، الزام تغییر رمز و دسترسی کارتابل مقصد در سرور بررسی می‌شوند.
- تصمیم صریح تازه مالک: پیامک صف مشترک برای **همهٔ افراد مجاز همان مرحله** با پذیرش هزینه بیشتر. پیش از ارسال هر مخاطب، پس از هر انتظار شبکه، مجوز دوباره بررسی می‌شود. پیامک مالک مستقل از اعلان مرحله بعد است؛ استثنای مشاهده مدیر موجب ارسال شخصی نمی‌شود.
- اعلان تأیید گروهی، هدف واقعی هر ردیف دارد؛ سقف نگهداری۱۰۰۰ است تا فرمان مصوب۲۰۰ردیفی/۴۰۰اعلان خودش را حذف نکند. این صندوق، بایگانی دائمی تاریخچه مالی نیست.
- پرداخت مشترک برای هر مالک/شرکت، پیام خصوصی با جمع **فقط سهم خودش** و شناسه‌های همان رسید می‌سازد؛ retry ثبت‌شده اعلان مالی تازه تولید نمی‌کند. فیش اصلی، تخصیص و مبلغ مالی تغییر نمی‌کنند. تغییر سرپرستِ کار منتظر به شخص جدید اعلان می‌دهد.
- ایجاد شرکت تازه دیگر مجوز سایر نقش‌ها را خودکار گسترش نمی‌دهد؛ دسترسی‌های موجود دست‌نخورده‌اند. اعطای شرکت جدید باید در مدیریت نقش صریح انجام شود.
- گزارش از همان snapshot مجاز تهیه می‌شود. index فیش فقط محلیِ همان محاسبه است و تطبیق دقیق شناسه/عضویت/اولین duplicate را حفظ می‌کند. کش بین کاربران/مجوزها ساخته نمی‌شود. کش محدود تاریخ صرفاً حساب تقویمی عمومی است، نه مجوز یا حد تاریخ درخواست.
- مسیر API محاسبه را دسته‌ای به event loop واگذار می‌کند؛ خروجی جزئی یا موفقیت زودرس ندارد. پیش از پاسخ، نشست، اختیار و باقی‌ماندن تمام منابع در projection مجاز جاری دوباره سنجیده می‌شوند. لغو دسترسی وسط گزارش،401/403 بدون report می‌دهد. قرارداد JSON، جمع‌های دقیق، سقف۵۰هزار، validation و خطای ledger حفظ می‌شوند.

## آزمون و حدود

آزمون‌های `notification-delivery`, `notification-session-api`, `notification-sms-journey`, `receipt-index`, `financial-report`, `report-concurrency-api` و regressionهای موجود مرجع بازتولیدند. scheduler gate فقط preload فرایند مصنوعی آزمون است، نه hook/auth mock در محصول. provider واقعی پیامک در آزمون‌ها خاموش است؛ موفقیت routing به معنی ارسال واقعی SMS نیست.

بار تعریف‌شده:۱۵ تیم چهارنقشی،۶۰ نشست مستقل،۱۰k سابقه، ثبت/بررسی/برگشت/رد/ویرایش/پرداخت جزئی و نهایی/retry و۳خواننده گزارش هم‌زمان. معیار p95 ثبت پایدار≤۵ثانیه شامل صف و تکمیل state است. آغاز سرد، زمان گزارش، p99 و منابع جدا گزارش شوند؛ نتیجه تضمین ظرفیت آینده،soak یا۱۰۰هزار سابقه نیست. اعداد نهایی از گزارش release خوانده شوند، نه نتیجه candidate قبلی.
