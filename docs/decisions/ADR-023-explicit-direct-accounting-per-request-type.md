# ADR-023 — ارسال صریح نوع درخواست به حسابداری با حفظ سرپرست سازمانی

Accepted — درخواست مالک۲۰۲۶/۱۰/۲۴؛ فقط توسعه/آزمون و Staging. این تصمیم محدودیت «بدون گزینه مستقل دورزدن سرپرست» در ADR-022 را برای همین انتخاب مصوب جایگزین می‌کند؛ دیگر قواعد آن ثابت‌اند.

## هدف، مرز و قرارداد

هرکدام چهار انتخابگر کاربر سه حالت دارند: پیش‌فرض سازمانی، تأییدکننده مشخص، یا «مستقیم به حسابداری». انتخاب سوم فقط همان نوع ثبت جدید را مستقیماً Pending_Accounting می‌کند؛ سرپرست سازمانی کاربر حذف نمی‌شود و انواع دیگر تغییر نمی‌کنند. stage/تأیید ساختگی یا خودتأییدی افزوده نمی‌شود. مدیریت از همان users/save و مجوز جاری مدیریت کاربران، CAS و audit قبلی است؛ سرپرست بدون آن مجوز، اختیار تازه نمی‌گیرد و هیچ actor مسیر حساب خودش را تغییر نمی‌دهد.

مقدار افزایشی User.requestApprovers[type] می‌تواند string قدیمی(userId) یا object دقیق `{mode:'ACCOUNTING'}` باشد؛ absence همان fallback قدیمی است. object به جای magic userId انتخاب شد تا با شناسه واقعی یا مقدار خالی اشتباه نشود. parser سختگیر، مقایسه semantic و UI سه‌حالته باید این تمایز را حفظ کنند. schema SQLite۱ ثابت؛ داده/رمز/نقش/کلید/مسیرهای قبلی بدون backfill/reset باقی می‌مانند. downgrade بهv58a پس از نوشتن marker مجاز نیست؛ بازیابی باCURRENTstate وroll-forwardسازگار است.

## مسیر متصل و حفاظت

مدل/parse/equality → اعتبارسنجی تنظیم و audit/CAS → resolver ثبت جدید → parent.supervisorId=null → حسابداری مجاز همان شرکت/رکورد. اعلان و SMS فقط مخاطبان واقعی حسابداری را می‌گیرند، نه سرپرست سازمانی صرف. مشاهده سازمانی موجود، الزاماً ازبین نمی‌رود اما اختیار تأیید سرپرست یا مخاطب اعلان ایجاد نمی‌کند. اصلاح/ارسال مجدد/عودت فنی از snapshot پرونده‌اند و از پروفایل جدید محاسبه نمی‌شوند. درخواست‌های قدیمی، حتی با تغییر تنظیم بهحسابداری، نزد مسئول قبلی باقی‌اند؛ درخواست جدید مستقیم نیز با برگشت حسابداری و تغییر پروفایل دوباره سرپرست پیدا نمی‌کند.

marker ارجاع یک شخص نیست؛ تنظیم مستقیم باید از validation/future-user-reference/delete-user checks به عنوان userId عبور نکند. رابطه سرپرست سازمانی و کارهای باز قبلی همچنان حفاظت می‌شوند؛ این گزینه راه پاک‌کردن مسئولیت قبلی نیست. بانک،مبلغ،سقف و گزارش/پرداخت فعلی تغییر نمی‌کنند.

## معیار پذیرش و ترتیب اجرا

۱) RED برای سه‌حالته و چهار فرمان، سپس کوچک‌ترین اصلاح parser/equality/resolver/UI. ۲) API برای چهارنوع، اختلاط مسیرها، نامعتبر/جعل/مدیرخود/کاربرغیرمجاز، CAS/object-clone/شکستcommit/restart، حفظ داده قدیمی وfuture refs. ۳) اعلان پرتال/SMS شبیه‌سازی‌شده و نشست‌های سرپرست/حسابداری؛ بازگشت عادی و فنی بهمسیر snapshot. ۴) buildfreeze،suite هرadapter، مرورگرواقعیRTL/mobile/refresh/ذخیره سه‌حالت. ۵) بازبینی خواندنی مستقل، بکاپ جاریStage/restore مستقل وhealth باحفظACCESS/vault. ۶) تحویلcandidate تازه، بدونProduction/commit/push یا تماس واقعی.

هدف این الحاقیه رفع پنجfindingقدیمی ممیزی نیست؛ نتیجه آزمون همین محدوده و محدودیت‌های شناخته‌شده در رکورد Stage جدید ثبت می‌شود.
