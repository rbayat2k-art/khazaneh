# ADR-002 — نقش‌های تکمیلی و مسیر بدون سرپرست

Status: Accepted — تصمیم مالک در ۲۰۲۶/۱۰/۲۱؛ شواهد انتشار در README.

## زمینه و تصمیم

به‌روزرسانی مصوب۲۰۲۶/۱۰/۲۲: مالک بعداً تأیید کرد «فقط شرکت‌های مجاز؛ در چندنقشی اجتماع شرکت‌های نقش‌ها». این تصمیم فقط بخش company allowlistِ توضیح اولیهٔ پایین را supersede می‌کند؛ سقف و scope عمومیِ نقش اصلی همچنان خودکار جمع نمی‌شوند. قرارداد جاری `src/server/company-access.ts:6–26` و [قواعد کسب‌وکار](../engineering/business-rules.md) است. بخش اولیه برای تاریخچه حفظ شده است.

یک شخص ممکن است حسابدار و سرپرست، یا سرپرست و متقاضی باشد. مدل `User.additionalRoles` و جمع مجوزها از قبل وجود داشت، اما انتساب و ذخیره در فرم کاربر کامل نبود. همان قرارداد تکمیل شد؛ حساب موازی، نقش ترکیبی ثابت، تغییر schema یا reset داده لازم نیست.

- نقش اصلی، صفحهٔ شروع و پیش‌فرض محدوده/سقف را حفظ می‌کند. نقش تکمیلی مجوزها را OR می‌کند، نه سقف یا محدوده را. override صریح کاربر پس از جمع اعمال می‌شود؛ صفر، اختیار صفر می‌ماند.
- ADMIN فقط نقش اصلی است. انتساب نقش/تغییر محدوده و سقفِ خود کاربر مجاز نیست. کاربر عادی مجوز مدیریت نقش پیدا نمی‌کند مگر مدیر آن را صریحاً بدهد.
- طبق تأیید مالک، یک فرد مجاز می‌تواند هر دو مرحلهٔ **درخواست شخص دیگری** را جداگانه تأیید کند. تأیید درخواست خود برای غیرادمین همچنان ممنوع است؛ استثنای موجود ادمین بازطراحی نشده است.
- داشتن مجوز خواندن گسترده، اختیار تصاحب مرحلهٔ سرپرست دیگران نیست. مرحله، ارجاع و سقف سرور کنترل می‌شوند. رابط مرحله و نسخه را می‌فرستد؛ برای کاربر دارای هر دو کارتابل، API عمومی بررسی بدون مرحله رد می‌شود تا تکرار اقدام، مرحله بعد را خودکار تأیید نکند.
- طبق تأیید مالک، درخواست **جدید** بدون سرپرست به حسابداری می‌رود. ارسال مجدد همین مسیر را حفظ می‌کند؛ اعلان و متن رابط با آن همسو است. نبود مرحلهٔ سرپرست نباید به تولید تأیید/شناسه/زمان ساختگی در loader منجر شود. سوابق قبلی خودکار جابه‌جا یا پاک نمی‌شوند.
- حذف نقش منتسب مسدود است. ازبین‌رفتن صلاحیت سرپرستی در حضور کار منتظر/زیرمجموعه، جانشین معتبر می‌خواهد؛ دسترسی، سقف ردیف‌ها، خودتأییدی و چرخهٔ سرپرستی جانشین بررسی می‌شوند.

## حدود و حفاظت

این تغییر هیچ نقش واقعی را خودکار به فردی نمی‌دهد و رکورد مالی قبلی را اصلاح نمی‌کند. JSON خام محلی جایگزین دادهٔ سرور نمی‌شود. UI فعلی، نقش اصلی و نشست موجود حفظ شده‌اند. آزمون‌ها با loopback، fixture مصنوعی و خدمات بیرونی خاموش اجرا می‌شوند. مرحلهٔ انتشار باید snapshot جدیدِ سازگار داده/تنظیمات و بازگشت بدون حذف داده داشته باشد.

Windows Application Control ابزار esbuild را مسدود می‌کند؛ سیاست آن تغییر نکرد. برای آزمون از حذف نوع داخلی Node موجود و برای بستهٔ سرور از Rolldown موجود در زنجیرهٔ Vite استفاده شد؛ وابستگی نصب یا ارتقا نیافت. بستهٔ سرور، API و مرورگر واقعی با هم آزموده می‌شوند؛ موفقیت یک bundler جای پذیرش مسیر کاربر نیست.
