# ADR-013 — اتصال‌های مستقل و قرارداد عمومی استعلام بانکی

وضعیت: تصمیم و پیاده‌سازی مصوب مالک، فقط candidate Staging v42؛ انتشار Production مجاز نیست.
تاریخ: ۲۰۲۶/۱۰/۲۳. مبنا: درخواست مالک برای عدم وابستگی نام/تنظیمات به یک سایت و ادامهٔ تست واقعی محدود ADR-012.

## تصمیم

تکمیل مصوب مالک۲۰۲۶/۱۰/۲۳،v44: فرم اتصال/کلید،انتخاب سرویس،فعال‌سازی/شرکت/سقف واعتبار فقط در **مدیریت اطلاعات پایه→تنظیمات استعلام کارت و شبا** نمایش داده شوند. صفحهٔ عملیاتی **تکمیل و استعلام شبا** فقط وضعیت خواندنی ونام اتصال فعال،ابزارها ونتایج را نگه دارد؛میان‌بر تنظیمات فقط برای مجوز مدیریت جاری وcanManageسرور. این جداسازی UI است،نه جایگزین authorizationAPI؛قرارداد/vault/کلیدهای قبلی تغییر نمی‌کنند.

هستهٔ استعلام از قرارداد `inquiry-client.ts` استفاده می‌کند؛ پاسخ خام ارائه‌دهنده از adapter خارج نمی‌شود. `inquiry-providers.ts` registry سمت سرور شامل descriptor محدود فرم، validator و factory هر قرارداد است. فعلاً **فقط یک adapter واقعی** مطابق مستند ارائه‌شدهٔ مالک وجود دارد. نام عمومی آن در UI «REST — استعلام کارت و شبا (قرارداد ۱)» است. نام دلخواه اتصال را مدیر تعیین می‌کند؛ ادعای پشتیبانی خودکار همه سایت‌ها/کلیدها نداریم.

مدیرِ دارای مجوز جاری و محدودهٔ سراسری می‌تواند تا۲۰ اتصال مستقل بسازد، کلید/تنظیمات همان اتصال را تغییر دهد و اتصال فعال را صریحاً انتخاب کند. ذخیره/انتخاب هیچ تماس شبکه‌ای ایجاد نمی‌کند؛ نبود نتیجه یا خطا مجوز failover/Retry خودکار نیست. حذف اتصال/کلید و fallback خودکار به سرویس دیگر اضافه نشده‌اند. کلید حذف‌شده از patch یعنی حفظ قبلی؛ مقدار خالی جایگزین کلید نمی‌شود. تمام قواعد شرکت، سقف روزانه، operationKey، مجوزهای جاری و عدم تغییر مبلغ/صف/تأیید/نام قبلی حفظ‌اند.

## محرمانگی و دوام

`secrets/inquiry-connections.enc` catalog نسخه۱ AES-256-GCM است؛ تنظیمات، credentialها و انتخاب فعال در یک نوشتن CAS اتمیک با fsync/rename ذخیره می‌شوند. KEK خصوصی موجود `secrets/keys/master.key` حفظ می‌شود. مقدار کلید هرگز در metadata، DB، localStorage، لاگ، تصویر یا پاسخ API نیست؛ فقط وضعیت وجود هر فیلد قابل مشاهده است. schema مالی SQLite تغییر نکرده است.

سازگاری v41: **فقط نبود catalog** موجب خواندن vault قبلی `cardinfo.enc` به‌عنوان «اتصال اصلی» می‌شود. اولین نوشتن، تمام کلید قبلی را داخل catalog جدید حفظ می‌کند و فایل قبلی را تغییر/حذف نمی‌کند. revision عمومی پس از import افزایشی می‌ماند؛ catalog خراب/ناشناخته fail-closed است و legacy را دوباره فعال نمی‌کند. نگهداری فایل legacy برای بازیابی نیست که پس از تغییر کلید جدید، آن را دوباره فعال کنیم؛ rollback امن روی داده/vault جاری یا roll-forward لازم است.

revision catalog برای CAS، generation هر profile برای تغییر تنظیمات/کلید، و generation انتخاب فعال مستقل‌اند. ویرایش اتصال غیرفعال، پاسخ اتصال فعال را باطل نمی‌کند؛ A→B→A generation تازه دارد. هر job، منبع، شناسه adapter و اتصال و generation را حفظ می‌کند. client و context ارسال از یک snapshot ساخته می‌شوند؛ claim/dispatch/apply مجوز و نسل جاری را دوباره می‌سنجند. operationKey قبلی بعد از تعویض اتصال فقط همان رسید قبلی است، نه تماس جدید. UI نسخهٔ اتصال تأییدشده را با درخواست می‌فرستد؛ تغییر هم‌زمان اتصال قبل از ثبت، هزینه را به اتصال جدید منتقل نمی‌کند.

## مرز شبکه و توسعهٔ بعدی

در Staging، auto/batch واقعی همچنان ممنوع و فقط lookup تک‌ردیفی دستی با تأیید هزینه مجاز است. خروجی شبکه backend بسته است؛ supervisor موجود فقط دو عملیات typed و endpoint ثابت/HTTPS/بدون Redirect قرارداد فعلی را اجرا می‌کند. registry مجوز URL، header، auth-template، کد یا parser دلخواه از مرورگر نیست. افزودن ارائه‌دهنده دیگر نیازمند مستند قرارداد، adapter با auth/پارامترها/اعتبارسنجی پاسخ مستقل، descriptor و تست آن، allowlist دقیق broker و مجوز مصرف داده/اعتبار همان سرویس است. رابط فعلی، نام بانک/صاحب حساب و مبلغ را به‌صورت خودکار عوض نمی‌کند.

این نسخه تغییری در پیکربندی/کلید Production نمی‌دهد؛ مسیر env قبلی Production فقط برای سازگاری محفوظ است. actual lookup/اعتبار با کلید مالک در این مأموریت **NOT RUN**؛ ابزارها فقط با کلید/پاسخ مصنوعی تست شده‌اند. کلید واقعی را مالک در UI خصوصی وارد می‌کند، نه در چت. شواهد اجرا و نسخهٔ فعال در راهنمای عملیات و checkpoint v42 هستند.
