# ADR-026 — نسخهٔ فرم اصلاح و پذیرش جاری خروجی

Accepted برای پیاده‌سازی و Staging،۲۰۲۶/۱۰/۲۵؛ مالک صریحاً رفع F01/F03، آزمون کامل، حفظ داده/رمز/دسترسی و عدم حذف کد اضافی را خواست. Production و Git push جدید مجاز نیستند؛ [رکورد گیت قبلی](../operations/release-v60-gate.md) شواهد RED را نگه می‌دارد.

## نیاز و قرارداد

۱. اصلاح معمولی تکی/کودک گروه باید نسخهٔ دیده‌شده هنگام بازشدن فرم را بفرستد. expectedVersion صحیح مثبت اجباری است؛ legacy واقعاً بدون نسخه۱است، نه نسخهٔ والد گروه. پذیرش و مقایسه در همان نوبت نویسنده و commandDb، پیش از تغییر مبلغ/پیوست/audit/اعلان انجام می‌شود. فرم کهنه409 و بدون اثر؛ ارسال تکراری باعث نسخه یا اعلان دوم نشود. خطای commit اجازه موفقیت کاذب یا retry خودکار با نسخه جدید نمی‌دهد.

۲. مرز ویرایش‌ها حفظ شود: پیش از اولین رسیدگی، همان فیلدهای فرمِ مجاز ADR-003؛ پس از برگشت عادی فقط مبلغ،شرح،مدرک افزایشی و برای پرداخت/کودک گروه کارت/شبا/بانک؛ مشخصات مالک،شرکت،نوع،ارجاع،گیرنده و مرکز در resubmit باز نمی‌شوند. اصلاح فنی خزانه همان allowlist فنی، گیرنده معین و تأییدهای ثابت دارد. تغییر حساس عادی همچنان تأیید قبلی را طبق منطق موجود باطل می‌کند. newAttachments غیرخالی به مجوز پیوست جاری نیاز دارد؛ [] مجاز است. هیچ تأیید یا قاعده مالی جدید اختراع نمی‌شود.

۳. خروجی عملیاتی/شبا و چاپ فیش، canExportReports مؤثر سرور را لازم دارند. endpoint خواندنی `POST /api/treasury/export` فقط selectionشناسه‌ای می‌پذیرد؛ OPERATIONAL باpool/uids،IBANباtargetsنسخه‌دار،PRINT_RECEIPTباreceiptId. ردیف/مبلغ/فایل/شرکت ارسالی کاربر منبع خروجی نیست. نشست، منوی مربوط و projection جاری دوباره خوانده می‌شوند؛ انتخاب حذف‌شده/خارجscope/مرحله‌عوض‌شده رد می‌شود. خروجی عملیاتی به canAccessTreasuryReports وابسته نیست. ساخت Excel همان builder/ستون‌ها/مبالغ/تفکیک نوبت‌های قبلی است؛ شبا همان قواعد اعتبار/منبع واقعی Stage را حفظ می‌کند، بدون dispatch یا مصرف اعتبار تازه.

۴. UI، handler و آخرین اثر async نیز guard دارند. پاسخ معوق پس از خروج/تغییر حساب/تغییر اختیار شناخته‌شده/خروج از صفحه نباید download/print کند. چاپ،فیش فعلیِ scopedرا به DOM می‌دهد؛ modalبسته‌شده دوباره باز نمی‌شود. اکسل+انتقال فقط پس از خروجی موفق، فرمان انتقال مستقلِ مجاز را می‌فرستد؛ رد/خطای شبکه هیچ انتقالی نمی‌کند. انتقال و پرداخت بدون اکسل، دریافت مدرک و قالب عمومی همچنان مستقل‌اند؛ چاپ metadata فیش همان ORِ مجوز پیوست/بایگانی قبلی را همراه canExportReports حفظ می‌کند.

## اثر داده و حفاظت

### تکمیل مصوب مالک پس از گیت JSON

suite کامل نخست JSON، یک نقص قدیمی و مستقل از F01/F03 را آشکار کرد: بازنویسی مستقیم و هم‌اندازه در Windows می‌تواند dev/ino/size/mtimeNs/ctimeNs یکسان نگه دارد. diagnostic مصنوعی۲۰۰فایلی،۱۵برخورد واقعی و۱۵خواندن کهنه ثبت کرد؛ بازاجرای تصادفاً سبز قرارداد را ترمیم نمی‌کرد. مالک در همین نوبت صریحاً افزودن رفع این مورد سوم را تأیید کرد؛ بدون توسعهٔ مجوز به Production یا پاک‌سازی.

در JSON، امضا اکنون metadata+SHA256 بایت‌های واقعی است؛ parse همان bytes هش‌شده را مصرف می‌کند و cache فقط decode/freeze تکراری را حذف می‌کند. refresh و assertCurrent محتوا را بازبینی می‌کنند؛ پیش از rename draft کهنه رد و پس از rename هر عدم‌تطابق با encoded دقیق نوشته‌شده، cache باطل و خطا می‌شود. سرور encoded را یک‌بار برای write/fsync/rename/publication می‌سازد. SQLite، صف نویسنده، retry محدود همان rename و schema ثابت‌اند؛ بدون reset، domain retry یا restore.

هزینهٔ آگاهانه: هر freshness/CAS خواندن+هش O(size) JSON دارد؛ سنجش محدود مصنوعی باید عدد و محدودیت، نه ظرفیت تجاری PASS، گزارش کند. قرارداد یک نویسنده باقی است: fingerprint و rename در برابر نویسندهٔ خارجی غیرهمکار، قفل یا CAS اتمیک بین آخرین check و rename نمی‌سازند. این اصلاح برخورد قابل‌مشاهده را تشخیص می‌دهد، نه مجوز چندنویسندگی JSON. پنج regression جدید برخورد metadata، stale/فساد محتوا، race خواندن، race publication و encoded دقیق را بدون sleep یا اتکا به دقت ساعت آزمون می‌کنند. سه تست برخورد قبل اصلاح RED ثبت شدند.

schema۱، بدون migration/backfill/reset، تغییر رمز/مجوز نقش یا حذف module/dependency. این API خروجی read-only است، در صف نویسنده ثبت نمی‌کند و actor/bodyهای فرمان پرداخت به آن تزریق نمی‌شوند؛ فقط نشست سروری صاحب آن است. oldclients بدون version باید فرم را تازه کنند؛ پذیرش بی‌نسخه برای سازگاری، باگ اصلی را برمی‌گرداند. نسخهٔ فرم هنگام click با نسخهٔ تازهٔ state جایگزین نشود.

## گیت‌ها

RED مشخص روی همان v60 و تست جدید قبل از اصلاح؛ API/unit مثبت/منفی چهارنوع،دوچرخه،کودک/legacy،مالک/مرحله/field injection،race/replay/commit failure/restart؛ export capabilityfalse و session/scope/menurevocation،ورودی جعلی،شبا ناقص و دوپرداخت جزئی؛ مرورگر واقعی stale dialog و تمام خروجی‌ها،پاسخ معوق/لغو دسترسی/شبکه/تغییر حساب؛ build/typecheck و suite کامل هر دو adapter روی artifact frozen؛ مرور مستقل و بکاپ جاری Stage/restore مستقل/برابری state و vault/ACCESS، سپس health. هیچ PASS جای نتیجهٔ اجرا‌نشده یا پذیرش مالک را نمی‌گیرد. فشار تازه لازم فرض نشود؛ این گیت ادعای ظرفیت نیست.

Recovery با CURRENT state/vault و binary سازگار/roll-forward؛ DB منجمد قدیمی روی ثبت تازه restore نشود. این تغییر نیز v57b را برای metadata و مسیرهای جدید سازگار نمی‌کند. نتایج و محدودیت‌های اجرای واقعی در رکورد v61 ثبت می‌شوند.

تحویل واقعی [v61b فقط Staging](../operations/staging-v61-revision-export.md): هر۴۹۵تست هر adapter،۱۰گروه مرورگر،۵بازاجرای استعلام و recovery/حفظ آخرین state/رمز/نقش/vault PASS؛ manifest=`0efae2b038c6f983a44e39de0f0c04517cf46d04795da08c70deeea07f8c29be`. پذیرش مالک و Production NOT RUN؛ شکست‌های میانی و هزینه/محدودیت JSON در همان رکورد محفوظ‌اند.
