# ADR-020 — انتخاب صریح شرکت‌های مجاز نقش

## وضعیت و مجوز

مصوب مالک،۲۰۲۶/۱۰/۲۴: کنترل «شرکت‌های مجاز نقش» به فرم نقش‌ها اضافه شود؛ فقط شرکت مشترک فعلیِ دو کاربر مورد اشاره برای نقش سرپرست مجاز شود، تا مالک بتواند انتساب سرپرست را انجام دهد. توسعه، تست و انتشار همین محدوده روی دامنه صریحاً مجاز است؛ چرخهٔ تأیید تکراری برای همین درخواست لازم نیست. انتساب کاربر، تغییر بقیه نقش‌ها یا دسترسی همهٔ شرکت‌ها مجاز نشده است.

## علت و قرارداد

شرکت پروفایل کاربر انتساب سازمانی است، نه مجوز خواندن/اقدام؛ این مرز مستقل در `companyPolicy` اجرا می‌شود. عنوان سرپرست با داشتن سه مجوز، محدوده و سقف کافی نیست؛ شرکت درخواست‌کننده نیز باید در اجتماع شرکت‌های مجاز نقش‌های سرپرست باشد. فرم فعلی این فهرست را نشان نمی‌دهد، هرچند API و کنترل سرور آن را دارند.

- UI همان فرم نقش و کلاس‌های فعلی را نگه می‌دارد. شرکت‌های catalog با checkbox و شرح تفاوت پروفایل/دسترسی نمایش داده می‌شوند. انتخاب جدید با ID ثابت ذخیره می‌شود؛ نام قدیمیِ معتبر نیز خوانده می‌شود. چندنقشی همچنان اجتماع نقش‌هاست؛ فهرست خالی هیچ شرکتی مجاز نمی‌کند، به‌جز قاعدهٔ ویژهٔ مدیر کل که تغییر نمی‌کند.
- metadata-only save فهرست را ارسال یا canonicalize نمی‌کند؛ مقدار قدیمی و ناسازگاری‌های دیگر دست‌نخورده‌اند. مقدار ناشناختهٔ قدیمی قابل مشاهده/حذف است، نه grant جدید. اختیار ADMIN همچنان همهٔ شرکت‌هاست و این فهرست برای آن در فرم فقط‌خواندنی توضیح داده می‌شود.
- UI فقط تغییر شرکت‌ها را همراه snapshot قبلی آن‌ها می‌فرستد؛ سرور برای snapshot نادرست409 می‌دهد. فهرست غیراستاندارد یا شرکت ناشناختهٔ جدید رد می‌شود؛ مجوز مدیریت نقش و مرز شرکت مدیر محدود همچنان در middleware برقرار است. هیچ startup enrichment، schema/migration یا grant از روی شرکت پروفایل انجام نمی‌شود.
- audit تغییر فهرست را با شمارش قبل/بعد ثبت می‌کند، بدون چاپ مقادیر محرمانه در گزارش بیرونی.

## اثر، آزمون و انتشار

مسیر: AdminPortalView → کنترل شرکت → roles/save → companyPolicy → فهرست سرپرستان/کارتابل/فرمان. تست مثبت/منفی، ID و نام، legacy ناموجود، metadata save، CAS، مدیر محدود، چندنقشی، same-session revoke/reload و مرورگرRTL/mobile لازم است. دادهٔ مصنوعی فقط در harness مستقل؛ ظاهر قبلی حفظ شود. مرجع محصول Khazaneh است، نه مسیرهای تاریخی TAPRA که supporting skill به آن‌ها اشاره می‌کند؛ فقط ردیابی متصل و gate متناسب آن به‌کار می‌رود.

پیش انتشار، همان binary منجمد در Staging و Linux تمرین، بکاپ و restore مستقل از دادهٔ جاری، بازگشت CURRENT و کنترل سلامت لازم‌اند. تنظیم زنده فقط با API مجاز و CAS، در پنجرهٔ بستهٔ ورودی انجام شود: فقط `APPROVER.allowedCompanies`، metadata و audit مربوط تغییر کنند؛ سایر نقش‌ها، رمزها، سقف، رابطهٔ سرپرست کاربران و تمام داده‌های مالی/فایل‌ها برابر بمانند. ID شرکت از catalog جاری و تطبیق دو کاربر resolve شود، نه مقدار حدسی یا fixture. rollback کد نباید همین تنظیم مجاز تازه یا ثبت‌های جدید را پاک کند.
